# Kernel-Enforced Sandboxing

sysg configures kernel enforcement mechanisms per service: today that means
rlimits, capabilities, namespaces, and cgroups (Linux, root); the roadmap
completes seccomp, `no_new_privs`, and Landlock.

## What enforces today

```yaml
services:
  worker:
    command: "./worker"
    user: "worker"
    limits:
      nofile: 4096
      cgroup:
        memory_max: "512M"
    capabilities: ["CAP_NET_BIND_SERVICE"]
    isolation:
      network: true
```

## Enforced today (schema v3, Linux)

Under `version: "3"`, these are really enforced by the kernel:

- **`isolation.landlock: { ro_paths, rw_paths }`** — a Landlock filesystem
  sandbox (Linux 5.13+). Paths not listed become inaccessible.
- **`isolation.seccomp: "baseline-v1"`** — a frozen, deny-by-default syscall
  allowlist; unlisted syscalls return `EPERM`. `no_new_privs` is set alongside.

```yaml
version: "3"
services:
  worker:
    command: "./worker"
    isolation:
      seccomp: "baseline-v1"
      landlock:
        ro_paths: ["/usr", "/lib", "/etc/worker"]
        rw_paths: ["/var/lib/worker"]
```

An unsupported kernel or a malformed policy **refuses the service**
([SG0722](/how-it-works/dialog/codes#sg0722)/[SG0724](/how-it-works/dialog/codes#sg0724))
rather than running it unprotected. `baseline-v1` is frozen; a different or
stricter policy will ship as `baseline-v2`, never as a silent edit.

## Still unenforced — read this

`isolation.apparmor_profile` and `isolation.selinux_context` are accepted by
the schema but **warn and run the service unenforced** under v2. Treat them as
documentation, not protection.

The planned semantics
([RFC 0001](https://github.com/ra0x3/systemg/blob/main/rfcs/0001-kernel-mode.md))
are uniformly **fail-closed**: any security key that cannot be enforced
refuses to start the service.

<Warning>
**Deprecation in progress.** As of v0.63, every unenforceable security key
(`seccomp`, `apparmor_profile`, `selinux_context`, `private_devices`,
`private_tmp`) logs a deprecation warning at service start: a future release
will refuse these keys with
[SG0721](/how-it-works/dialog/codes#sg0721)/[SG0722](/how-it-works/dialog/codes#sg0722)
instead of running unprotected. Remove the keys or plan for the refusal —
the flip lands behind a manifest schema bump.
</Warning>

## Planned diagnostics

- [SG0721](/how-it-works/dialog/codes#sg0721) — sandbox capability
  unsupported on this platform
- [SG0722](/how-it-works/dialog/codes#sg0722) — seccomp filter could not be
  built or applied; service refused
- [SG0723](/how-it-works/dialog/codes#sg0723) — `no_new_privs` could not be
  set; service refused
- [SG0724](/how-it-works/dialog/codes#sg0724) — Landlock requested but the
  kernel ABI is unavailable or insufficient; service refused
